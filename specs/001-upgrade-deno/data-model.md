## Entities NOT touched

The following entities are intentionally out of scope for this upgrade PR
(per the spec's `CHANGELOG.md` clarification):

- `CHANGELOG.md` — runtime pin bumps are housekeeping and do not warrant
  an `[Unreleased]` entry under the constitution's CHANGELOG policy.
- `deno.json` — `version`, `imports`, `unstable`, `compilerOptions`,
  `lint`, `fmt`, `nodeModulesDir` are unchanged.
- `deno.lock` — `version: 5` schema is still accepted by 2.9.2; the
  resolver output is regenerated by `deno task compile:mcp` /
  `deno task check:mcp-deno` automatically and is not hand-edited.
- `deno.json#version` (the package version, `0.2.0-alpha4`) — bumping the
  package version is a release concern, not a runtime concern, and is
  gated by the Release workflow only when the package version actually
  changes.
- Library exports (`src/index.ts`), public types, MCP tool surface,
  relation-kind registry, solver-tag tuple — all spec-frozen under
  Constitution Principle II (Wire Stability); the version bump MUST NOT
  introduce a wire change.

## State transitions

None. The bump is a static literal change plus the derived artifacts
(refreshed lockfile entries and refreshed host binary), both produced
mechanically by the existing task suite.

## Validation rules

- After the literal update, `scripts/compile-mcp.sh` and
  `scripts/check-mcp-deno.sh` MUST accept the host's installed Deno
  (which MUST be `2.9.2`) without producing a "version mismatch" error.
- After the literal update, running `deno task check:npm-allowlist` MUST
  still pass (the npm allowlist is independent of the Deno pin).
- After the literal update, `deno task lint` MUST NOT introduce new
  lint findings on existing code (TS 6.0's strict defaults add no new
  offenders per research.md item 6).
