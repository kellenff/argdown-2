# Phase 0 Research: Cut argdown-2 v1.0.0 Release

**Date**: 2026-08-07
**Spec**: [spec.md](spec.md)
**Plan**: [plan.md](plan.md)

This research resolves the cut-mechanics questions that arose
during planning. Every finding traces back to a concrete file in
the repo or a step in `release.yml`. No external research was
required — the v1 cut is bounded by the existing automation.

## Decision 1: Order of version-pin updates

**Decision**: Update all six version pins in a single PR commit,
not across multiple commits.

**Rationale**: The constitution's parity tests
(`src/claude-plugin.test.ts:43-91` and `src/pi-package.test.ts:43-59`)
fail if any one of the six pins is out of sync with another.
Splitting the update across multiple commits would leave a window
in which `deno task test` is red on `main`, which the
`pull-request CI` workflow blocks (`Constitution §"Development
Workflow & Quality Gates"`). A single commit keeps CI green
throughout and produces one bisectable cut point.

**Alternatives considered**:
- Per-channel PRs (one for JSR, one for binaries, one for
  marketplace, one for Pi). Rejected: leaves the parity tests red
  on `main` between PRs and creates N release PRs to coordinate.
- Per-file commits. Rejected: same as above, plus clutters the
  history.

**Mechanics** (specific files and line-level diffs):
- `deno.json:3` — `"version": "0.2.0-alpha4"` →
  `"version": "1.0.0"`.
- `scripts/argdown-2-mcp.version:1` —
  `0.2.0-alpha4\n` → `1.0.0\n`.
- `plugins/argdown-2/scripts/argdown-2-mcp.version:1` —
  `0.2.0-alpha4\n` → `1.0.0\n` (byte-equivalent to canonical,
  enforced by `src/claude-plugin.test.ts:85-91`).
- `plugins/argdown-2/.claude-plugin/plugin.json:4` —
  `"version": "0.2.0-alpha4"` → `"version": "1.0.0"`.
- `package.json:3` — `"version": "0.2.0-alpha4"` →
  `"version": "1.0.0"`.
- `package-lock.json:3,9` — both root
  `"version": "0.2.0-alpha4"` references regenerated by running
  `yarn install --mode=update-lockfile` (or the user's lockfile
  manager of choice).
- `src/mcp/server.ts:21` — `{ name: "argdown-2", version:
  "0.2.0-alpha4" }` → `{ name: "argdown-2", version: "1.0.0" }`.

## Decision 2: Compile invocation strategy

**Decision**: Use `bash scripts/compile-mcp.sh --all` (the same
invocation `release.yml:158` uses).

**Rationale**: `compile-mcp.sh:53-61` accepts `--all` to compile
all four targets, defaulting to host-only without it. The release
workflow always uses `--all` because CI runs on
`ubuntu-latest` (`release.yml:38`) and must produce all four
binaries. The host developer running the cut locally (typically on
`aarch64-apple-darwin`) should also use `--all` so the host binary
matches what CI produces — no host-vs-CI drift.

`compile-mcp.sh:30-33` enforces that the local Deno matches
`scripts/deno-version`; if it does not, the script exits 1
before any compile step runs. This is the canonical "Deno pin
parity" gate.

**Alternatives considered**:
- Host-only compile, then download CI artifacts. Rejected: the
  GitHub Release does not exist yet at cut time (it is created by
  the cut itself), so there are no CI artifacts to download.
- Cross-compile from a single host. Rejected: Deno does not
  cross-compile; each target requires a host of matching
  triple or emulation.

## Decision 3: Stdio probe invocation

**Decision**: Run `deno run -A scripts/probe-mcp-stdio.ts
./dist/mcp-bin/argdown-2-mcp-x86_64-unknown-linux-gnu` after the
compile step, exactly as `release.yml:160-162` does.

**Rationale**: `scripts/probe-mcp-stdio.ts` validates the
`initialize` + `tools/list` handshake against a compiled binary
and prints the tool names. CI runs the same probe against the
Linux binary only (`release.yml:160-162`) because CI is hosted on
`ubuntu-latest` (`release.yml:38`); the three non-Linux binaries
are covered by the compile-step success only.

The probe confirms:
- The binary launches and accepts an MCP `initialize` request.
- `tools/list` returns the 14-tool contract.
- No startup panic / unhandled rejection.

**Alternatives considered**:
- Probe all four binaries locally. Rejected: redundant with CI
  and inconsistent with the existing `release.yml` workflow. The
  Apple/Linux cross-builds happen in CI; the local cut should
  match CI exactly to surface drift early.

## Decision 4: Checksum generation

**Decision**: Run the `release.yml:Generate checksums` step
verbatim (or its local equivalent). The output is
`dist/mcp-bin/sha256sums.txt` with exactly four lines, one per
binary, in alphabetical target order.

**Rationale**: The release workflow at `release.yml:164-177`
emits exactly this format. The launcher (`scripts/argdown-2-mcp`
`verify_checksum` at line 32-56) accepts both bare names and
path-prefixed names (per `scripts/argdown-2-mcp.test.sh:63-78`
"path-prefixed checksum" case), so the `release.yml` format is
forward-compatible.

**Alternatives considered**:
- Generate checksums in a different order. Rejected: `release.yml`
  pins the order alphabetically by target triple; deviating
  produces a different `sha256sums.txt` than CI, which the
  launcher's checksum entry lookup tolerates but reviewers
  diffing local vs CI artifacts will not.

## Decision 5: CHANGELOG closure shape

**Decision**: Replace the `[Unreleased]` heading with
`[1.0.0] - 2026-08-07`; preserve all content beneath (the
`### Added` / `### Changed` / `### Removed` blocks already
present in the current `[Unreleased]` section); delete the 7-line
alpha-rollback preamble that immediately follows the
`[Unreleased]` heading; append a fresh empty `[Unreleased]`
section if follow-up work is pending; preserve the
`[0.2.0-alpha4]` link reference at the file footer.

**Rationale**: Q1 confirmed preamble deletion; FR-007 confirmed the
date format; the file footer reference is needed for historical
pinning (Constitution §II wire stability).

The new `[1.0.0] - 2026-08-07` section starts with `### Added`
(the first `### ` heading after the preamble is deleted). The
`release.yml:Extract CHANGELOG notes` step (`release.yml:179-196`)
extracts everything between the `## [1.0.0]` line and the next
`## [` line into `release-notes.md`; deleting the preamble
ensures the GitHub Release body starts with `### Added` rather
than with the rollback explanation.

**Alternatives considered**:
- Keep the preamble in past tense. Rejected by Q1 (clarification
  session).
- Move the preamble to a new `### Notes` subsection. Rejected:
  adds noise to the v1 release body that downstream consumers
  must scan past.

## Decision 6: PR / merge workflow

**Decision**: Open a single PR (`002-v1-release` branch →
`main`) carrying all six version-pin updates + CHANGELOG closure
+ `package-lock.json` regeneration. PR CI runs every Deno gate
(FR-008 / SC-005). On green merge, `release.yml:stable-release`
detects the `deno.json#version` bump and runs the stable-release
job.

**Rationale**: `release.yml:113-137` `Detect version bump`
compares `deno.json#version` against `HEAD~1:deno.json#version`
and flags `changed=true` only when the strings differ. PR merge
to `main` triggers `release.yml` via the `on.push.branches: [main]`
hook (`release.yml:16-17`).

The PR description (per Q5) is the announcement surface: it
should link to the v1 baseline spec and explicitly state "this
PR cuts v1.0.0".

**Alternatives considered**:
- `workflow_dispatch` with a version override
  (`release.yml:18-22`). Considered as a fallback if the
  `on.push.branches: [main]` trigger misses the bump (e.g.,
  because the merge commit's `deno.json` is identical to its
  parent's). Not needed in the happy path but useful to know
  about.

## Decision 7: What ships if a gate fails after merge

**Decision**: If a CI gate fails after the version-bump PR is
merged but before the tag is pushed, the release engineer
amends the merge commit (or pushes a follow-up fix) to restore
green CI. `release.yml` does not auto-rollback; it waits for
green.

**Rationale**: The spec's Edge Case 1 covers this
(`specs/002-v1-release/spec.md:222-225`). The release workflow
does not have a "skip release on gate failure" branch — it
assumes the merge commit is green. If CI fails post-merge, the
fix must land before any tag is pushed; otherwise
`release.yml:stable-release` may ship a binary produced from a
broken commit.

**Alternatives considered**:
- Add a `--dry-run` mode to `release.yml`. Rejected: out of
  scope for this cut; this would be a separate PR if added at
  all.

## Decision 8: What is in the `1.0.0` GitHub Release body

**Decision**: The body is the byte-equal content of the
`[1.0.0] - 2026-08-07` section of `CHANGELOG.md` as extracted by
`release.yml:Extract CHANGELOG notes` (`release.yml:179-196`).

**Rationale**: SC-003 locks this exact contract. The release
workflow uses `body_path: ${{ steps.notes.outputs.notes_path }}`
(`release.yml:215`) which loads the extracted file verbatim.

**Alternatives considered**:
- Hand-write a release body in the workflow. Rejected:
  introduces drift between `CHANGELOG.md` and the GitHub Release
  body, which the constitution explicitly forbids (the
  `Extract CHANGELOG notes` step exists to prevent this).
